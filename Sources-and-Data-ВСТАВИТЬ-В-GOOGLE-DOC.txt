Sources and Data
Регламент источников данных и спецификация отчёта

Статус: действующая редакция.
Тип документа: нормативно-методический регламент проекта.
Назначение: установить единые правила для источников данных сайта crypto-academy-pro.onrender.com, а также зафиксировать требования к структуре и содержанию отчёта «СКАМ‑МОНИТОРИНГ».
Область применения: фронтенд, бэкенд, внешние сервисы, сценарии ручного обновления, автоматические пайплайны, публикация метрик, таблиц и аналитических выводов.
Документ согласован с официальным отчётом «СКАМ‑МОНИТОРИНГ | Source & Data» (PDF) и используется как базовый стандарт для подготовки, проверки и публикации данных.

Назначение документа
Документ определяет:
1. какие источники разрешено использовать для формирования метрик сайта;
2. какие требования предъявляются к дневному отчёту и временной линии событий;
3. как должна формироваться таблица «Объекты и риск»;
4. по каким правилам интерпретируются жалобы, признаки риска и итоговые статусы;
5. какие служебные блоки должны сохраняться для корректной работы автоматических обновлений.

Ключевые принципы
1. Проверяемость. Каждая цифра, ссылка, жалоба и формулировка должны быть прослеживаемы до конкретного источника.
2. Единообразие. Один и тот же тип данных должен оформляться по одинаковым правилам во всех разделах документа и на сайте.
3. Достоверность. Запрещено дополнять документ предположениями, неподтверждёнными обвинениями и вымышленными значениями.
4. Воспроизводимость. Ручная и автоматическая сборка документа должны давать согласуемый результат.
5. Служебная совместимость. Формулировки и блоки, используемые скриптами, должны сохраняться в совместимом формате.

Структура документа
Документ состоит из трёх функциональных частей:
1. Часть I. Регламент источников данных для сайта и связанных метрик.
2. Часть II. Спецификация отчёта «СКАМ‑МОНИТОРИНГ», включая правила поиска, таблицы и оценки риска.
3. Приложение. Служебные блоки, необходимые для автоматического обновления документа и сохранения таблиц.

ЧАСТЬ II. СПЕЦИФИКАЦИЯ ОТЧЁТА «СКАМ‑МОНИТОРИНГ»
═══════════════════════════════════════════════════════════════

В данном разделе зафиксированы обязательные требования к структуре отчёта за день, формату временной линии, таблице «Объекты и риск» и правилам заполнения всех аналитических полей.

—————————————————
ТЗ.1. Структура документа по дню
—————————————————
• Для каждого дня создаётся один лог‑блок:
  — Период: DD.MM.YYYY 00:00 – DD.MM.YYYY 23:55 (MSK)
  — Время формирования: DD месяц, 23:55 MSK
• Ниже идёт раздел «Временная линия дня:» и строки событий по времени.
• Внутри одного дня: время идёт по возрастанию от 00:00 до 23:55; каждая отметка времени (HH:MM) используется не больше одного раза; запрещено копировать один и тот же блок событий (одно время и те же каналы) многократно.
• Списки каналов не пишутся в лог по времени. Все каналы и детали по ним фиксируются только в таблице.

Правила по времени (обязательно)
1. Для каждого дня в документе используется только один диапазон:
   — Период: DD.MM.YYYY 00:00 – DD.MM.YYYY 23:55 (MSK)
   — Время формирования: DD месяц, 23:55 MSK
2. Внутри «Временной линии дня» время всегда идёт по порядку, от 00:00 до 23:55.
3. Каждое значение HH:MM можно использовать только один раз за день.
   Если уже записана строка на 03:00, в этот день второй строки «03:00 — …» быть не должно.
4. Пример правильной последовательности (00:00, 00:05, 00:10, 00:20, 00:30):
   — 00:00 — Начат сбор данных за период 00:00–23:55.
   — 00:05 — TGStat/Telega: найдено каналов по фильтрам — TGStat 0, Telega 0.
   — 00:10 — За последние 10 минут новых объектов по фильтрам не найдено, источники доступны.
   — 00:20 — TGStat/Telega: найдено 12 новых сигнал‑каналов, добавлены в таблицу «Объекты и риск».
   — 00:30 — За последние 10 минут новых объектов по фильтрам не найдено, источники доступны.
5. В лог по времени запрещено вставлять длинные списки каналов. Лог фиксирует только:
   — сколько найдено объектов,
   — где искал,
   — были ли ошибки/недоступные источники.

—————————————————
ТЗ.2. Формат временной линии
—————————————————
Формат строки: HH:MM — краткое описание события (одна строка).

Пример блока:

Период: 07.03.2026 00:00 – 07.03.2026 23:55 (MSK)
Время формирования: 7 марта, 23:55 MSK

Временная линия дня:
00:00 — Начат сбор данных за период 00:00–23:55.
00:05 — TGStat/Telega: найдено каналов по фильтрам — TGStat 0, Telega 0.
00:10 — За последние 30 минут новых объектов по фильтрам не найдено, источники доступны.
00:20 — TGStat/Telega: найдено каналов по фильтрам — TGStat 0, Telega 53.
…
23:55 — Завершён сбор данных за день, таблицы обновлены.

Правила: лог отвечает только на «когда» и «что в общем произошло» (нашли/не нашли, сколько, был ли перерасчёт); никаких списков @каналов и «(3/6 рисков)» в логах.

—————————————————
ТЗ.3. Маршрут поиска (где и как искать)
—————————————————
Порядок действий при поиске каналов и жалоб.

Шаг 1. Поиск каналов (Telegram)
1. В каталогах Telegram и в глобальном поиске Telegram ищи каналы по ключевым словам:
   crypto signals, крипто сигналы, VIP signals, pump, x2, x5, profit, заработок, доход, без риска.
2. Отбирай только те каналы, которые: связаны с криптой/трейдингом; дают сигналы или обещают доход; продают VIP, курсы, платные подписки.
3. Каналы, которые просто дают новости/аналитику без продажи сигналов и дохода, отмечай как «крипто‑канал (новости)» и статус «без риска (новости/аналитика)» или вообще не включай в таблицу риска.

Шаг 2. Поиск жалоб в Telegram
1. Используй чаты, посвящённые скаму и жалобам (которые уже заданы в настройках), и ищи там: по названию/юзернейму канала (@username); по словам «скам», «обманули», «развод», «слил депозит», «мошенники».
2. Фиксируй: сколько разных людей жалуются (по никам); какие формулировки они используют («после оплаты VIP заблокировали», «слил депозит по их сигналам»).
3. В таблицу в столбец «Жалобы / отзывы» пиши короткое резюме:
   «2 человека в чате X пишут, что после сигналов канала слили депозит (без суммы).»
   «В чате Y жалуются, что после оплаты VIP автор перестаёт отвечать.»

Шаг 3. Поиск отзывов в интернете
Для каждого найденного канала/сайта:
Примеры запросов: «имя канала» + отзывы / «имя канала» + scam / «имя канала» + обман / «имя канала» + развод / «имя канала» + жалобы.
Где искать: форумы по трейдингу/крипте, комментарии под статьями, посты в соцсетях, где обсуждают этот канал/бот/сайт.
В таблицу заноси только то, что реально нашли. Если ничего не нашли — писать: «Жалоб в открытых источниках не найдено (поиск по Telegram и интернету).»

ТЗ.4.2. Правила заполнения ячеек строки
Каждая строка (N ≥ 2) соответствует одному объекту (канал, бот или сайт).

Столбец 1 — Объект / ссылка
• Для канала: текст @username и гиперссылка https://t.me/username на этот же текст.
• Для сайта/курса: текст example.com и ссылка https://example.com.
• Если ссылка не открывается или объект не про крипту/сигналы — строку вообще не создавать.

Столбец 2 — Тип
Одно короткое значение, например: сигнал‑канал, крипто‑канал (новости), бот, сайт/курс, обучение. Никаких описаний здесь, только тип.

Столбец 3 — Источник
Откуда взяли объект: каталог Telegram, поиск в Telegram, чат с жалобами, поиск в интернете. Допускается до двух источников через «+» (например, каталог + жалобы).

Столбец 4 — Краткое описание
1–2 предложения по факту, что делает объект. Примеры: «Канал даёт торговые сигналы по криптовалютам и обещает высокий процент успешных сделок.» / «Публикует новости рынка без продажи сигналов или VIP.» Только то, что реально видно в описании и постах. Без оценок «мошенники», «плохой».

Столбец 5 — VIP / деньги
Как объект зарабатывает. Примеры: «VIP‑подписка 15 000₽ / месяц»; «Есть закрытый VIP‑канал, цена не указана, просит писать в личку»; «Платных услуг не обнаружено.» Только реальные данные. Никаких выдуманных цен.

Столбец 6 — Жалобы / отзывы
Итог по жалобам. Примеры: «2 человека в чате X пишут, что после сигналов слили депозит (без суммы).» / «На форуме Y есть отзывы, что после оплаты VIP автор перестал отвечать.» / «Жалоб за период не найдено (поиск по чатам и интернету).» Если сумм нет — не придумывать. Если жалоб нет — честно писать, что не найдено.

Столбец 7 — Признаки риска (флаги)
Список конкретных флагов, каждый опирается на факт.

Структура/поведение:
• «новый канал (< 14 дней)»
• «есть дорогой VIP (от ~10 000₽)»
• «обещания x2/x5, „без риска“, „гарантированный доход“»
• «много картинок монет со стрелками вверх/вниз»
• «объяснения по монетам короткие, без сценариев риска»
• «активно продаёт VIP („пиши в ЛС“, „осталось мало мест“)»
• «показывает только прибыльные сделки, убытки не показывает»

Дополнительно, если используется VWAP‑анализ сигналов:
• «часто даёт лонги ниже VWAP (торговля против VWAP)»
• «часто даёт шорты выше VWAP»
• «сигналы сильно далеко от VWAP (>2–3% смещения)»

Флаги можно писать через запятую или с новой строки внутри ячейки. Ни одного флага нельзя придумать — только по реальному контенту/жалобам/сигналам.

Столбец 8 — Итоговый статус
Краткий вывод, основанный на столбцах 4–7:
• «в риске (структура + поведение + жалобы)»
• «поведенческий риск (жалоб нет)»
• «жалобы, но мало данных по контенту»
• «без риска (новости/аналитика)»
• «под наблюдением (мало данных)»

Статус никогда не ставится «из головы», только как резюме предыдущих столбцов.

Обязательный чек-лист для каждого сигнального канала
При внесении каждого канала в таблицу необходимо проверить и зафиксировать:
1. Структура: новый или старый канал (примерно по дате создания/активности); есть ли VIP/платная подписка, курс, закрытый клуб; есть ли обещания дохода («x2 за день», «без риска», «гарантированная прибыль»).
2. Поведение: использует ли картинки монет со стрелками вверх/вниз; даёт ли поверхностные «обоснования» на 3–5 строк без сценариев риска; постоянно ли зовёт в VIP/личку («пиши в ЛС», «успей в VIP»); показывает ли убытки или только прибыльные сделки.
3. Жалобы: есть ли реальные жалобы в чатах и интернете; есть ли истории про слив депозита, обман с VIP, блокировку после оплаты; есть ли указанные суммы потерь (если да — фиксируй).
Результаты проверки отражаются в столбцах «Краткое описание», «VIP / деньги», «Жалобы / отзывы», «Признаки риска (флаги)» и «Итоговый статус».

Требование к достоверности данных
Допустимые источники выводов и формулировок.
1. Все выводы должны опираться только на: реальные посты и описание канала; реальные сообщения в чатах; реальные страницы и комментарии в интернете.
2. Запрещено: придумывать жалобы и суммы потерь; придумывать признаки риска («мошенники», «кидают»), если это не подтверждается контентом или жалобами; приписывать каналу то, чего нет в его постах.
3. Разрешено и правильно: писать «жалоб не найдено»; писать «цена не указана»; писать «мало данных, объект под наблюдением», если информации действительно мало.

Цель системы и принципы аналитической оценки
—————————————————

Этот блок задаёт не просто фильтр по жалобам, а основную логику интерпретации. Система должна искать и оценивать каналы так, чтобы в первую очередь выявлять психологическую токсичность и нарушения риск-менеджмента, даже если канал выглядит «успешным» или по нему пока мало жалоб.

1. Основная цель системы
Система должна находить и анализировать крипто-телеграм-каналы с сигналами (новые и старые) так, чтобы:
1) В первую очередь выявлять психологически токсичные и рискованно устроенные каналы, а не только те, про которые уже есть жалобы.
2) Оценивать канал не по одному признаку («жалобы» или «прибыль»), а по комбинации:
   • психология и язык;
   • риск-менеджмент;
   • структура контента;
   • связи с другими каналами;
   • динамика поведения со временем.
Риск-менеджмент и психологическое воздействие важнее, чем аргумент «иногда сигналы работают».

2. Критерии психологической токсичности
Токсичный канал — это не только грубость, крик или мат.
Токсичность = любой вид психологического давления + нарушение риск-менеджмента, даже если всё подано мягко, красиво и в формате «заботы».
Система должна считать токсичным:
1) Прямое давление:
   • «если не зайдёшь — останешься нищим»;
   • «нормальные люди уже зарабатывают, только ты в стороне»;
   • «кто не с нами — тот проиграл».
2) Мягкое давление через «заботу» и «мечту»:
   • «я хочу, чтобы вы наконец вылезли из нищеты, заходите в эту сделку»;
   • «это шанс изменить жизнь, не упустите»;
   • «я за вас переживаю, поэтому рекомендую зайти побольше».
3) Азарт и подталкивание к превышению риска:
   • «зальёмся по максимуму»;
   • «можно брать плечо побольше, шанс 99%»;
   • «сейчас отличный момент удвоиться, потом не будет».
4) Нарушение риск-менеджмента в рекомендациях, даже при мягком тоне:
   • призыв заходить без стоп-лосса;
   • намёки «можно зайти крупнее обычного»;
   • игнорирование ограничений по риску;
   • советы «усредняться до победы» или «отбить убыток объёмом».
Если язык или поведение канала подталкивает людей играть, а не аккуратно торговать, канал должен уходить в высокую зону риска.

3. Риск-менеджмент как ключевой критерий
Для этой системы риск-менеджмент важнее результата отдельных сигналов.
Правила:
1) Если канал нарушает риск-менеджмент и/или подталкивает людей:
   • заходить слишком крупно;
   • усредняться до смерти;
   • торговать без стопов;
   • увеличивать риск после убытка,
   он автоматически попадает в наивысшую категорию риска, даже если:
   • у него иногда «везёт»;
   • сигналы бывают прибыльные;
   • жалоб пока мало или нет.
2) Канал, который:
   • честно использует стопы;
   • признаёт убыточные сделки;
   • не подталкивает «зайти всем депозитом»,
   может быть убыточным, но это не делает его токсичным. Ошибки на рынке не равны токсичности.
3) Если канал говорит одно, а делает другое, это усиливает риск:
   • если в общих постах он пишет про важность риска;
   • но в реальных сигналах предлагает нарушать риск-менеджмент,
   это считается отягчающим фактором, а не оправданием.

4. Порядок анализа нового канала
Для каждого нового канала нужно проходить несколько уровней анализа.

4.1. Уровень 1 — Структура (паспорт канала)
Нужно собрать:
• примерный возраст канала (по первым постам и статистике);
• тему (крипто-сигналы, памп, арбитраж, обучение и т.п.);
• наличие платных продуктов:
  • VIP чат;
  • курс;
  • платный бот;
• как оформлены обещания:
  • есть ли в описании и закрепах обещания дохода, x2/x5, «без риска», «гарантированный заработок».
На этом уровне система фиксирует структуру, но ещё не делает окончательный вывод.

4.2. Уровень 2 — Язык и психология
Нужно анализировать последние 50-100 постов и фиксировать:
1) На какие эмоции давит канал:
   • страх упустить шанс (FOMO): «не упусти», «такого больше не будет»;
   • стыд и сравнение: «все уже в рынке, только ты тормозишь»;
   • жадность и лёгкие деньги: «ничего не делая, будешь получать X»;
   • псевдо-заботу: «я хочу вытащить вас из бедности, поэтому зайдите крупно».
2) Как канал говорит о риске:
   • упоминает ли вообще слова «риск», «стоп», «может не сработать»;
   • есть ли честные фразы о неопределённости;
   • или он пишет только «точно», «гарантия», «всегда в плюс».
3) Как канал относится к ошибкам:
   • есть ли посты, где автор признаёт убытки и разбирает ошибки;
   • или все посты только про успешные сделки;
   • а убытки перекладываются на подписчиков («вы сами виноваты»).
4) Как он общается с подписчиками:
   • уважительно и спокойно;
   • или с унижением, давлением и обвинениями.
Результат этого уровня — психологический профиль канала: сколько в нём давления и манипуляции, а сколько честности и уважения.

4.3. Уровень 3 — Поведение в сделках и риск-менеджмент
Нужно смотреть не только на язык, но и на реальные сигналы и рекомендации.
Для нескольких последних серий сигналов система проверяет:
• указаны ли стоп-лоссы и адекватные уровни риска;
• нет ли прямых или скрытых призывов:
  • «зайти всем депозитом»;
  • «усредняемся до победы»;
  • «увеличим объём, чтобы отбить убыток»;
• честно ли показываются убыточные сделки:
  • пишет ли автор «стоп забрал», «сделка не зашла»;
  • или просто замалчивает все минусы.
Если канал:
• регулярно нарушает риск-менеджмент;
• подталкивает увеличивать риск без достаточного основания,
он должен относиться к самому высокому уровню риска, даже без явных жалоб и даже при наличии успешных сделок.

4.4. Уровень 4 — Связи с другими каналами
Система должна смотреть:
• кого этот канал рекламирует;
• кто рекламирует этот канал;
• нет ли среди них уже известных токсичных каналов;
• не копирует ли он тексты, скрипты продаж и шаблоны подогрева у плохих каналов:
  • одинаковые продающие сценарии;
  • идентичные формулировки;
  • повторяющиеся обещания, связки и «легенды».
Если новый канал встроен в сеть уже токсичных каналов, это усиливает риск даже тогда, когда жалоб ещё мало.

4.5. Уровень 5 — Сравнение с нормальными каналами
Система должна иметь набор адекватных эталонных каналов, которые:
• регулярно напоминают о риске и ограничениях;
• показывают и плюсы, и минусы;
• не давят на психику;
• говорят про платные продукты редко и без подачи «это твой единственный шанс».
Каждый новый канал нужно сравнивать с этими эталонами:
• если он намного меньше говорит о риске;
• намного больше давит и продаёт чудеса;
• показывает только успехи,
его нужно смещать в сторону токсичной зоны, даже если жалоб ещё нет.

5. Принципы интерпретации убытков и платных продуктов
Важно отделять токсичность от обычной рыночной ошибки.
1) Убытки сами по себе не делают канал плохим. Если:
   • есть стопы;
   • автор честно признаёт минусы;
   • нет давления «зайти всем депозитом»,
   такой канал не должен попадать в токсичную зону только из-за потерь.
2) Платность — это норма. Канал может брать деньги за VIP, курс или подписку и при этом оставаться нормальным, если:
   • уважает риск;
   • честно говорит о неопределённости;
   • не манипулирует страхом и жадностью.
3) Токсичным делает не факт оплаты, а стиль и риск. Система не должна «душить» честные платные каналы. Она должна жёстко выделять тех, кто:
   • нарушает риск-менеджмент;
   • давит на психику;
   • продаёт иллюзию лёгких денег.

6. Обязательная инструкция для системы
Твоя задача — находить и анализировать крипто-каналы с сигналами так, чтобы:
• в первую очередь выявлять психологическую токсичность и нарушения риск-менеджмента;
• не оправдывать токсичное поведение тем, что «иногда сигналы работают»;
• отличать честные, но убыточные каналы от тех, кто подталкивает людей играть и превышать риск;
• учитывать, как канал говорит, что он реально советует делать с риском, с кем он связан и насколько его стиль близок к уже известным плохим каналам;
• сравнивать каждый новый канал с нормальными эталонами и видеть, насколько он уходит от них в сторону давления, манипуляций и азартной игры.
Любой канал, где есть психологическое давление и призывы нарушать риск-менеджмент, должен относиться к самой высокой категории риска, даже без жалоб и независимо от того, насколько часто у него «заходят» сигналы.

7. Режим поиска и требования к 5-минутному отчёту

7.1. Общий режим работы
1) Поиск должен всегда быть широким и глубоко тематическим. Никаких «быстрых проходов» только по одному каталогу.
2) У системы есть до 12 часов внутри периода, чтобы качественно находить каналы, их связи, жалобы и контекст.
3) Каждые 5 минут система не обязана «найти всё», но обязана коротко и честно отчитываться, что именно делала за этот интервал.
4) Весь поиск ориентирован только на крипто-каналы с сигналами / VIP / заработком. Обычные новости и аналитика по крипте не являются приоритетной целью.

7.2. Жёсткий запрет на 0,0 и поверхностный поиск
Запрещено:
1) Писать сухие строки вида: HH:MM — TGStat/Telega: найдено каналов — TGStat 0, Telega 0.
2) Считать поиск завершённым, если система:
   • посмотрела только 1-2 каталога;
   • использовала 2-3 простых ключевых слова;
   • не открывала описания, закрепы и посты каналов.
3) Писать «ничего не найдено», если поиск был ограниченным. В таком случае система обязана прямо указать, что поиск был ограничен, а не делать вид, что «в мире пусто».

7.3. Минимальный стандарт широкого поиска
Перед тем как написать, что по теме не найдено новых каналов или связок, система обязана пройти минимум:
1) Несколько типов источников:
   • каталоги и аналитические списки Telegram;
   • глобальный поиск по самому Telegram;
   • чаты или группы с жалобами и обсуждениями по крипте и трейдингу;
   • хотя бы одну свежую подборку, статью или обзор в интернете по крипто-каналам с сигналами.
2) Несколько групп запросов:
   • сигналы и сделки: signal, signals, сигналы, trade, trading, entry, long, short, take profit, stop loss, TP, SL;
   • деньги и чудеса: доход, заработок, profit, passive income, x2, x5, 100%, гарантия, без риска, risk free;
   • VIP и закрытые истории: VIP, закрытый канал, private, inner circle, подписка, плати, курс, обучение, приватный чат;
   • азарт и нарушение риска: отбить убыток, отыграться, слил, слив, залить, плечо, левередж, high risk, всё плечом.
3) Проверку внутреннего оформления каналов:
   • описания;
   • закреплённых сообщений;
   • хотя бы части последних постов, чтобы отличить сигналы и продажи от обычных новостей.
Если это не сделано, поиск считается неполным, и система не имеет права писать, что «ничего не найдено».

7.4. Фильтр по теме
При широком поиске система обязана отбрасывать из фокуса новостные и аналитические крипто-каналы, которые:
• не продают сигналы, VIP или курсы;
• не обещают доход;
• не давят на психику фразами вроде «успей» или «останешься нищим».
Приоритет остаётся только у:
• сигнальных крипто-каналов;
• каналов, ботов и структур с VIP, платными сигналами и курсами «как разбогатеть»;
• схем, где продвигается заработок на крипте с психологическим давлением и нарушением риск-менеджмента.

7.5. Формат отчётов каждые 5 минут
Каждые 5 минут система обязана описывать действия, а не только результат.
Правильный формат, если новых объектов не найдено, но поиск был широкий:
HH:MM — выполнен широкий тематический поиск по крипто-сигналам: проверены несколько Telegram-каталогов, глобальный поиск по Telegram, профильные подборки и чаты с жалобами по группам запросов (сигналы, VIP, «без риска», «отбить убыток», обучение). Новых релевантных каналов с признаками психотоксичности и нарушения риск-менеджмента за этот интервал не выявлено.
Правильный формат, если проход был только базовым и ограниченным:
HH:MM — выполнен только базовый проход по двум каталогам Telegram с ограниченным набором ключей (например, сигналы + VIP). По этим источникам новых релевантных каналов не найдено. Требуется расширенный поиск по другим источникам и дополнительным группам запросов.
В каждой 5-минутной строке дополнительно должны быть:
• 1-3 конкретные ссылки на реально проверенные страницы или найденные объекты;
• query groups или конкретные запросы, которые реально использовались в этот слот;
• честная пометка, был ли это wide pass или только limited pass.

7.6. Жёсткая формула для программы
1) Запрещено выводить сухие строки вида TGStat 0, Telega 0.
2) Любой отчёт об отсутствии новых каналов должен описывать:
   • какие типы источников проверены;
   • какие группы запросов использованы;
   • какие конкретные ссылки или reference URL были реально проверены;
   • что фильтрация шла именно по крипто-сигналам, VIP, заработку, психотоксичности и нарушению риск-менеджмента.
3) Система всегда работает в режиме широкого поиска, а не быстрого скана.
4) Пока не пройден минимум по нескольким источникам, нескольким группам запросов и базовой проверке описаний/постов, система не имеет права писать «ничего не найдено».

—————————————————
Модель объекта и система скоринга риска
—————————————————

Канал рассматривается не как одна строка в таблице, а как объект с признаками и историей.

7.0. Базовые принципы работы с данными
Система должна работать так:
1. Всю информацию брать только из реальных текстов: постов канала, жалоб в чатах и страниц в интернете — не придумывать сама.
2. Анализировать эти тексты по признакам структуры, поведения и связей и уже на основе этого строить выводы и скоринг.
3. Любой флаг риска, жалоба, сумма или вывод всегда опирается на конкретные найденные фразы/сообщения; при их отсутствии честно писать «нет данных» / «жалоб не найдено».
4. Все выводы и статусы в таблице и документе — результат этого текстового анализа, а не заранее заданных шаблонов («3 из 6»).
5. Любое обновление по каналу (новые жалобы, новая агрессия VIP и т.д.) появляется только после того, как в тексте действительно появились новые сообщения, посты или отзывы.

7.1. Модель
Канал — объект со статическими и динамическими признаками, связями и внутренним скорингом риска. Система собирает признаки, хранит историю минимум 14 дней, каждый день пересчитывает скоринг и статус.
Конкретно: статические признаки (что «вшито» в структуру); динамические (как ведёт себя со временем); связи (с кем перекликается, кого рекламирует); внутренний скоринг риска, обновляемый каждый день. Обязанность системы: собрать набор численных и логических признаков; хранить их историю минимум 14 дней; каждый день пересчитывать скоринг и статус.

7.2. Признаки уровня 1 — паспорт (статические)
Возраст (дни с первого поста), язык/регион, тип (сигналы / сигналы+обучение / памп / арбитраж), наличие платных продуктов (VIP чат, курс, платный бот), диапазон цен (дешёвый / средний / дорогой), формальные обещания («гарантируем», «без риска», «x2/x5», «100% профит»). Каждый пункт — флаг или число. Уже на этом уровне формируется базовый структурный риск.

7.3. Признаки уровня 2 — анализ контента
По последним ~100 постам система считает:
• Долю сигнальных постов / обучение / маркетинг VIP: сколько постов — сигналы (вход/выход/уровни), сколько — обучение/аналитика, сколько — прямой маркетинг VIP.
• Частоту слов про риск vs «гарантированно»: сколько раз — «риск», «stop», «SL», «может не сработать»; сколько — «точно», «гарантированно», «100%», «без риска». Результат: индекс честности про риск и индекс агрессивной уверенности.
• Баланс плюсов/минусов: количество постов про успешные сделки vs про неудачные/стоп‑лоссы; коэффициент однобокости (50 плюсов и 0 минусов — подозрительно).
• Давление VIP: доля постов с призывом в VIP/личку/закрытый чат; срочность («только сегодня», «последний шанс»).
• Длину и качество объяснений: средняя длина текстов при сигнале; доля сигналов с планом B/C (альтернативные сценарии); доля сигналов «картинка+2 фразы».
Итог: индексы прозрачности риска, агрессивного маркетинга, однобокости, пустых объяснений.

7.4. Признаки уровня 3 — связи и экосистема
• Исходящие связи: кого канал рекламирует; ссылки на VIP/бот/партнёров («наш VIP‑чат», «наш бот», «партнёр»).
• Входящие связи: кто рекламирует канал, в т.ч. из уже помеченных риском.
• Похожесть текстов/структуры на известные скам‑каналы (шаблоны приветствия, продающих постов, скрипты продаж VIP).
Результат: экосистемный индекс риска — канал новый «с нуля» или встроен в известную токсичную сеть.

7.5. Признаки уровня 4 — динамика 14 дней
Ведётся временной ряд по каждому индексу. Каждый день — пересчёт; сравнение с прошлым днём/неделей; производные (ухудшение/улучшение). Важно не только «что сейчас», но стало ли хуже (рост агрессивности, больше VIP, меньше разговоров о риске) или лучше (канал стал спокойнее, показывает минусы). Для каждого индекса — не только значение, но и производная (рост/падение за 3–7–14 дней).

7.6. Итоговый скоринг
Веса: структура ~30%, контент ~30–40%, связи ~20%, динамика ~10–20%. Шкала: 0–30 — низкий/наблюдение, 30–60 — поведенческий риск, 60–100 — высокий/скам. На выходе — человеческое объяснение: какие признаки, как менялись за 14 дней, почему «в риске» или «под наблюдением».

7.7. Блок-инструкция (обязательные правила оценки)
Текст блока-инструкции (вставлять без изменений):
Ты не имеешь права оценивать канал по принципу «есть жалобы / нет жалоб». Для каждого нового канала ты обязан: 1) Собрать структурные признаки (возраст, платные продукты, обещания дохода). 2) Проанализировать последние ~100 постов и посчитать: долю сигналов/рекламы/аналитики, индекс честности про риск, баланс плюсов и минусов, силу давления VIP, долю пустых объяснений. 3) Построить карту связей: с кем канал связан, на кого похож, с кем он в одной сети. 4) Вести историю этих показателей минимум 14 дней и каждый день пересчитывать: стало лучше / хуже, усилились или ослабли признаки скама. На основе всех этих уровней ты вычисляешь внутренний скоринг риска, но в документе всегда объясняешь человеческим языком: какие именно признаки ты увидел, как они менялись за 14 дней, почему ты решил, что канал «в риске» или «только под наблюдением».

7.8. Хранилище каналов с историей 14 дней
Место: backend/data/channel_objects.json.
Схема: корневой ключ channels — объект; ключ канала — нормализованный идентификатор (@username или t.me/username). По каждому каналу: first_seen, last_updated (YYYY-MM-DD), history — массив до 14 элементов вида { "date": "YYYY-MM-DD", "snapshot": { ... } } (от старых к новым). В snapshot на дату входят поля из текущей строки отчёта: obj, link, type, source, age, vip, growth, complaints, risk_analysis, title, has_complaints; зарезервированы поля для уровней 2–3–4: content_indices, connections, dynamics (пока null или {}).
Ежедневное обновление: после получения финальных risk_rows в run_12h_monitor вызывается merge_channel_snapshots(risk_rows, report_date_str): загрузка JSON, для каждой строки — нормализация id, добавление/обновление канала, добавление снимка на дату отчёта, обрезка истории до 14 дней, сохранение файла. Чтение истории в отчёте/на сайте пока не обязательно; достаточно накопления для следующих итераций (динамика, новый скоринг).

События за период — ниже
